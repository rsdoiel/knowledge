**Context.** DR-0006 noted that the `workspace:` reference qualifier does not say *which* workspace. DR-0007 found the problem was worse than a reference ambiguity: a workspace-tier record's identity was `(NULL project, "workspace", record_id)`, unique only *within* one workspace, and every workspace has an `agents/decisions/` that may hold a DR-0001. Ingesting two workspaces' tiers into one database was demonstrated to overwrite the first with the second and report it as a routine `1 updated`. The `uuid` guard added in W5 turned that silent loss into a reported failure, but a guard that refuses a legitimate record is a stopgap, not an answer. `~/Laboratory` was deliberately left without a workspace tier until this was settled.

The shape of the answer came from the user rather than from the code: `~/WorkLab` is the WorkLab workspace and `~/Laboratory` is the Laboratory workspace, and from the tool's point of view that is just the name of the parent directory. That is considerably smaller than what DR-0007 forecast, which assumed the workspace would have to become a `projects` row and take the NULL `project_id` — and DR-0004's `IFNULL` index — with it.

**Decision.** `records` gains a `workspace` column and the identity index becomes `UNIQUE(workspace, IFNULL(project_id, -1), scope, record_id)`. The name is `filepath.Base(root)`, where the root is the parent of the directory holding the database — `~/WorkLab/agents/knowledge.db` is `WorkLab` — exposed as `kb.Workspace()`. It is **derived, not stored**: no frontmatter field, so no record file changes and none of the 204 live records is rewritten. `RecordByIdentity` takes the workspace explicitly rather than reading it off the database, because ingest's `--root` may legitimately name a workspace other than the one the database sits in; `AddRecord` defaults an empty `Workspace` to the database's own. The index is renamed from `idx_records_scope_id` to `idx_records_identity`, and the old one dropped by name. Cross-workspace *references* stay inexpressible, so `workspace:NNNN` means the citing record's own tier — now unambiguously, because the record knows which workspace it belongs to.

**Rationale.** Deriving the name from the path is what makes this nearly free: there is no registry, no configuration, no new frontmatter field, and therefore nothing that can fall out of sync with anything else. `kb` already computed the root for storing relative paths, so the name was there to be read. Renaming the index matters more than it looks: `CREATE UNIQUE INDEX IF NOT EXISTS` would have found the old name present and silently kept the narrower index, leaving the defect in place on precisely the databases that already had records — the ones where it mattered. Backfilling existing rows from the database's own path is correct *because* of the bug: a database could only ever have held one workspace's records, since a second workspace's would have overwritten the first, so there is no ambiguity about what to backfill. DR-0004's `IFNULL` survives untouched, because the workspace tier still has no project and the NULL is still real — DR-0007's forecast that this change would retire it was wrong, and this record corrects that in passing.

**Rejected alternatives.** Storing each workspace as a `projects` row — the strawman DR-0007 assumed. It removes the NULL and so the `IFNULL` index, but it puts workspaces and projects in one namespace, which is exactly the collision the reference grammar would then inherit: `WorkLab:0002` would be indistinguishable from a project named WorkLab. Adding a `workspace:` field to the frontmatter — it makes the name authorable and therefore wrong-able, and would have rewritten all 204 records for information the path already carries. Keeping the `uuid` guard as the answer — it converts silent loss into a reported failure, which is better than nothing and worse than storing both records; the guard stays, but now only for a genuine same-workspace identity collision. Allowing cross-workspace references with a distinct syntax — the other workspace may not be checked out, which is the same reason supersession is same-tier only, and no such reference has ever been wanted.

**Consequences.** `go build`/`go vet`/`gofmt`/`go test` clean. The motivating case now behaves: ingesting `WorkLab/agents/decisions` and `Laboratory/agents/decisions` into one database reports `1 added` twice and stores both, each under its own workspace, where before it reported `0 added, 1 updated` and destroyed the first. The lazy migration was verified against a copy of the real `~/WorkLab/agents/knowledge.db`: 195 records backfilled to `WorkLab`, `idx_records_identity` created, `idx_records_scope_id` dropped, and 246 observations and 42 relations untouched. The check that matters most is the one after: re-ingesting all four corpora into the migrated copy reports every record **skipped**, not re-added, which is what proves the derived name matches the backfilled one. `~/Laboratory/agents/decisions/` is now safe to create — nothing further blocks it, though what its first record should say is a separate question. The `workspace:` qualifier's meaning is settled but its *documentation* is not: `DECISION_RECORD_FORMAT.md` still describes it without saying it is own-workspace only, and that wording belongs in a `WorkLab/agents/decisions` record amending DR-0002, not here.
