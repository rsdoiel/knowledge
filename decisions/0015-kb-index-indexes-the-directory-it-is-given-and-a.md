**Context.** Two tests were failing before W1 of the records-portability plan began, and both failed identically on a clean checkout, so neither was a regression from that work. They turned out to have nothing to do with each other.

`TestCmdIngest_ClasmCorpus` asserted `Added == 169`, `Supersedes == 2` and `RelatesTo == 3` against the live `~/WorkLab/clasm/decisions`. That corpus now holds 172 records and 9 `relates_to` edges. Nothing is wrong with it or with ingest; the test had written down a census of another repository on the day it was authored, and that repository kept being used.

`TestCmdIndex_ByteIdenticalToLiveIndexes` was more interesting. Its premise was explicit in its own comment: the live `index.md` files were generated by `~/WorkLab/decisions_index.ts`, so comparing against them compared two independent implementations. WorkLab DR-0003 retired that tool once `kb index` matched it, and it has since been deleted. What remained was a test comparing `kb`'s output against files `kb` itself had generated — no longer a cross-check, and structurally a report on whether every corpus in two workspaces had been re-indexed recently.

Underneath the expired premise it had caught something real. `collectRecordFiles` is a `filepath.WalkDir` and recurses unconditionally, and `index` and `ingest` shared it. On 2026-08-27 `~/WorkLab/agents/decisions/` gained a nested `caltechauthors/` corpus with its own `index.md` and its own DR-0001..0005, colliding one-for-one with the workspace tier's DR-0001..0006. Indexing the workspace tier therefore folded eleven records into one index containing two DR-0001s, two DR-0002s and so on.

The first reading of that failure was that the live `index.md` was stale. It was not. Every one of the six live indexes was correct, and `kb index` had regressed against a corpus layout that postdated it. That distinction is the whole finding: the tool was wrong and the data was right, which is the opposite of what a byte-comparison failure usually means and the reason this one was nearly dismissed as workspace hygiene.

Ingest was checked separately against a scratch database and is not affected. The nested records carry `project: caltechauthors`, so they ingest as project-tier rows while the workspace tier keeps its NULL `project_id`; the identities do not collide and recursion is correct there.

**Decision.** `kb index PATH` indexes the record files directly in `PATH` and does not descend into subdirectories. A directory that holds records is a corpus and owns exactly one `index.md`; a nested corpus is indexed by pointing at it. `kb ingest` keeps the recursive walk. The two verbs stop sharing one collector: `collectRecordFilesIn` is index's, `collectRecordFiles` stays ingest's, and the comment on each says why the other exists.

The byte-identical test is retired rather than repaired, and its place is taken by `TestCmdIndex_MatchesGoldenFixture` over a checked-in corpus at `cmd/kb/testdata/index-corpus`, covering an empty trigger, backticks and double quotes in a title, a supersession pair, and a record that is `accepted` while carrying `superseded_by`. `TestCmdIngest_ClasmCorpus` keeps the live corpus and counts it instead of remembering it.

**Rationale.** One directory, one index is the rule the format already implies — `kb index` writes exactly one file, at the path it was given, and there was never an answer to which of two nested corpora that file should describe. Recursion looked harmless while every corpus was flat, and stopped being harmless the moment one was not. Non-recursion needs no boundary marker and has no first-run problem: the alternative of stopping at any directory that already owns an `index.md` cannot see a brand-new nested corpus, because a corpus that has never been indexed has no `index.md` to be recognised by.

Splitting the two collectors is the point rather than a side effect. `index` and `ingest` want genuinely different discovery — one writes a file per directory, the other fills one database from a tree — and the shared helper had made that difference invisible enough that changing it for one verb would silently have changed it for the other.

Retiring the byte-identical test rather than pointing it at fresh files is the honest move. A test whose comparand is regenerated by the code under test asserts nothing once the second implementation is gone; keeping it would mean re-running `kb index` across two workspaces whenever it went red, which trains the failure to be dismissed. That is close to what happened here.

Counting the corpus rather than remembering it keeps what clasm is for. Its value is that it is large, old and hand-written, exercising frontmatter shapes no fixture would invent — not that it had 169 records on one particular day. The properties worth asserting are that every record file on disk produces exactly one ingested record, that a second run skips all of them and updates none, and that nothing fails; all three survive the corpus growing, and all three would still catch a real ingest defect.

**Rejected alternatives.** *Treat the nesting as a corpus-layout error in WorkLab.* No code change, and defensible while only one such tree exists — but the layout is reasonable, the tool gave no diagnostic, and the failure mode is an index silently describing records from a corpus it does not own. *Stop at any subdirectory holding its own `index.md`.* Preserves recursion for deep trees, at the cost of a boundary that does not exist until the first successful run. *Recurse and write one `index.md` per directory that holds records.* The most convenient, and it makes `--stdout` ambiguous about which of several indexes it is printing. *Regenerate the live indexes and keep the byte comparison.* Green today, red the next time anyone authors a record in either workspace, and still asserting nothing about `kb`. *Keep the clasm counts and update them.* Same failure on a timer, and it makes this repository's suite depend on another repository holding still.

**Consequences.** Implemented, and the whole suite is green: `go build`, `go vet` and `gofmt` clean, no skips beyond the existing "corpus not on this machine" guards. `go test -race` is expected to stay blocked on the Pi by the pre-existing ThreadSanitizer/VMA issue, unrelated to this.

The check that matters most is the one after the change: `kb index --stdout` now reproduces all six live indexes byte for byte — `agents/decisions`, its nested `caltechauthors`, `clasm`, `CMTools`, `cold` and `knowledge` — where before the change the workspace tier did not match. That is the evidence the live files were right and the tool was wrong, and it is the assertion the retired test was reaching for without being able to express.

`TestCmdIndex_TitleIsAlwaysField7` keeps its live corpora, deliberately: it asserts a structural property that new records cannot break, which is what a live-corpus test should look like. `kb-index.1.md` should say that index does not recurse; the man page describes a PATH without saying how far it reaches. Nothing here touches the records-portability work, which resumes at W2.
