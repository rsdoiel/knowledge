**Context.** W6 adds `kb index`, surfaces records through `kb search`, and makes records browsable in the TUI. Its acceptance criterion is unusually strong and unusually clear: byte-identical output against `decisions_index.ts` across every live corpus, which is what workspace DR-0003 set as the condition for deleting that tool. Three questions the plan leaves open had to be answered to get there. The plan says `kb index PATH` without saying whether the index is built from the record files or from the `records` table — a real choice, because the two can disagree whenever a record has been written but not yet ingested. It says nothing about a record that will not parse, where `ingest` has an established answer (report it, keep going) that turns out to be wrong here. And its search criterion — "a search whose top hit is a record body reports it as `record`" — collides with the fact that `kb_fts.kind` already holds the record's *own* kind, `decision` or `correction`, so satisfying it naively would mean discarding that.

**Decision.** `kb index` builds from the files. It takes a `*KnowledgeBase` for signature consistency with every other verb and never queries it, so the index can be regenerated in a checkout that has never been ingested, and a record written by `kb record new` appears in the index without an ingest step in between. A record that will not parse is **fatal** to `index`, where in `ingest` it is reported and skipped: ingest is building a partial view that a later run completes, while the index is a claim about what the corpus contains, and one that silently omits a record is worse than no index. `KBSearchResult` gains a `SourceType` field rather than remapping `Kind`, so a hit reports both that it is a record and that it is a `correction`. The TUI records view is read-only, consistent with the TUI's existing scope, and reverses `RecordsByProject`'s oldest-first result rather than re-sorting it, so the date-then-`record_id` ordering rule stays in exactly one place. Before deleting `decisions_index.ts`, its 25 tests were mapped against the Go suite and the four invariants Go did not yet cover were ported first.

**Rationale.** Building from files rather than the table is what makes `index` composable with `record new` and `record fmt`, none of which touch the database either — the file tree is the source of truth and the table is a derived index, so generating one derived artifact from another would add a synchronisation requirement for nothing. The fatal-parse decision is the one that departs from this module's established temperament, and it departs deliberately: every other non-fatal choice here — unresolvable references, out-of-vocabulary values, unquoted scalars — leaves a *recoverable* gap that a re-run closes, whereas a record missing from the index is invisible precisely to the reader the index exists to serve. Keeping `Kind` intact and adding `SourceType` costs one column in the projection and preserves information that a caller filtering for corrections would otherwise have to re-query for.

**Rejected alternatives.** Building the index from the `records` table — it would let `index` reuse `ListRecords` and its ordering, but it makes the index a function of the last ingest rather than of the corpus, so a freshly written record would be missing from it and a deleted one would persist in it. Reporting and skipping an unparsable record, matching ingest — see above. Overloading `Kind` with `record` — satisfies the plan's wording exactly and throws away the record's own kind. Re-sorting records in the TUI instead of reversing — a second implementation of an ordering rule that plan finding 3 exists to keep singular. Deleting the Deno tool first and porting its tests afterwards — the ported tests are what prove the replacement faithful, so porting after deletion would mean writing them against a specification no longer in the tree.

**Consequences.** `go build`/`go vet`/`gofmt`/`go test` clean; 303 tests, none skipped. `kb index` is byte-identical to `decisions_index.ts` on all five corpora — 169, 13, 7, 6 and 7 records, the largest a 25,446-byte file — and `awk` finds the title at `$7` on all 169 clasm rows. `decisions_index.ts`, its tests, its `deno.json` entries and its `bin/` artifact are removed under workspace DR-0003; the Deno suite goes from 68 tests to 43, and `decisions_split.ts` stays with its comment and its index-generation hint updated to name `kb index`. One behavioural difference is now permanent: `decisions_index.ts` skipped a frontmatter-less file as prose, while `kb index` errors, which the `NNNN-*.md` filter makes safe since real prose files never match. A gap this leaves, recorded as a finding in the WorkLab knowledge base rather than fixed here: the `kb` on PATH is 0.0.3 and has no `index` verb, so until the current build is installed there is no working index generator in that workspace at all, and nothing detects a stale index — it has no checksum guard, which is how the DR-0004..0006 promotions desynced it earlier the same day. W7 should consider whether `kb index` wants a `--check` mode that exits non-zero on drift, so a hook can enforce what nothing currently does.
