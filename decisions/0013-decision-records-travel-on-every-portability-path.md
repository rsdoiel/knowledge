**Context.** `agents/knowledge.db` has nine real tables. All three portability paths carry seven of them: `merge`, `export` and `import` each move `projects`, `concepts`, `sources`, `observations` and the three join tables, and none of them moves `records` or `record_relations`. The cause is ordering rather than disagreement — `merge` landed 2026-07-26..28, DR-0003 settled JSON-L export/import on 2026-08-08, and decision records arrived afterwards in DR-0004 through DR-0011 on 2026-08-25..26. Nothing went back.

This surfaced while planning the first real cross-machine merge, the one the whole UUID migration was built for. Both machines are now migrated and `kb merge` is ready to run, and running it today would drop all 13 of this machine's decision records into a merged file that reports success — `records` is absent from the hardcoded table list in `knowledge_merge.go:246` and equally absent from the per-table summary, so the output says nothing about the table it discarded. The second consequence is quieter but worse for the format: DR-0003 positions export/import as "the no-file-access alternative to `merge`", and an export that omits `records` cannot round-trip a database that has them, so the alternative is not equivalent to the thing it is an alternative to.

The workaround is real and insufficient. Re-running `kb ingest` against each `decisions/` directory after a merge does restore the records, because records derive from Markdown under git. But it requires file access, which is precisely what DR-0003 says one of these two paths must not require, and it depends on the operator already knowing about a loss the tool never reported.

**Decision.** `records` and `record_relations` are carried by `merge`, `export` and `import`, with the same identity, conflict and ordering rules on every path — DR-0003's equivalence treated as a standing requirement rather than a description. `record_relations` is a pure id-keyed join and remaps through record uuids the way `observation_concepts` remaps through its two endpoints, keeping the existing behaviour that an unresolvable reference is skipped rather than propagated. Records themselves move by **LEFT JOIN** through `projects`, not the inner join the observations path uses, because `records.project_id` is nullable by design and an inner join drops every workspace-tier record; a test asserts this by failing specifically on the inner-join version.

Collision handling generalises rather than forks: `CollisionReport` and `ReconcileCollisions` widen from a single `name` column to records' four-column identity, `(workspace, IFNULL(project_id,-1), scope, record_id)`. Where two sides agree on identity but their bodies differ, that is reported as **its own class** — a content divergence, listed separately from an identity collision, naming the records and both checksums — and it does not block the merge. A-wins stands.

Both paths index records into `kb_fts` as `source_type = 'record'`, including in `rebuildFTSIfNeeded`, which `merge` depends on entirely. `sources` stays out of that function. A schema-coverage guard on `merge` is deferred to its own record.

**Rationale.** Generalising the collision machinery is cheaper than it first appears because records are structurally the same problem it already solves: two rows that are one record logically, holding different uuids because they were created on different machines. The only real change is that the identity is four columns instead of one, so `NameCollision` stops being about names.

The left join is the finding most likely to have been missed by a careful patch that copied the neighbouring code. The observations path's inner join is correct *there* — `observations.project_id` is always populated — and it reads as the house pattern for moving a child table. Records break the assumption, and this machine already holds the row that proves it: one workspace-tier record with a NULL `project_id`, `agents/decisions/` DR-0001, created only after DR-0011 made the workspace tier safe to use. A pure count assertion would not catch this, since 12 of 13 records would still arrive.

Treating a content divergence as its own class, without blocking, is the narrow reading. Widening it — making a checksum mismatch abort — would be a new conflict policy, and the existing one is deliberate: `merge` and `import` both resolve in favour of the row already present and neither consults `updated_at`, which makes A-win deterministic rather than arbitrary. Inverting that is a change to two code paths and a migration, not a flag. But collapsing the divergence into an ordinary collision would be the wrong narrow reading, because a decision record's text *is* its artifact in a way a project's description is not; the operator needs to know which record's prose was dropped so they can reconcile the Markdown, and `checksum` already makes that detectable at no cost.

The FTS work is not a follow-up item. `kb_fts` has no triggers — it is maintained by explicit inserts at each write site, with `rebuildFTSIfNeeded` as a backstop that fires only when the index is empty — and that backstop indexes observations, projects and concepts only. A merge that correctly unioned `records` and stopped there would produce a database where `kb search` still cannot find a single record, which is the first thing anyone would check and the whole point of DR-0008 putting `source_type` in search output.

**Rejected alternatives.** *Document the `kb ingest` workaround and close it.* It restores the rows, but it makes file access mandatory on the path DR-0003 built to avoid it, and it leaves a tool that loses data while reporting success. *Exclude records from portability on the grounds that they are file-derived.* The `records` row carries `body` and `checksum`, so the database is already self-sufficient; the derivation is how records get in, not a claim about where they live. Excluding them would also make export strictly weaker than `merge`, breaking the parity DR-0003 rests on. *Block the merge on any checksum mismatch.* Safest-sounding and too strict: one drifted record stops an entire sync until it is resolved out of band, and the divergence is usually two machines having ingested the same file at different times rather than a genuine conflict. *Fix `sources` in the same pass.* It is a few lines in a function this work already touches, which is exactly the argument that makes unrelated changes ride along; it is a real gap and deserves its own decision about what a source's searchable text should even be. *Bundle the schema-coverage guard.* The guard is about how `merge` treats any table it does not know, including tables that do not exist yet — a different topic, and bundling it would make this episode record cover two.

**Consequences.** Not yet implemented; this record is the design decision, and the plan follows. The work is four pieces, TDD throughout with the failing test written first: generalise the collision machinery, union the two tables in `MergeKnowledgeBases` and add them to the summary, add both to JSON-L export and import, and index records into `kb_fts` on both paths. The acceptance criterion is an end-to-end test that currently has no coverage at all — merge two databases where each side holds records the other lacks, then assert the merged database has the union, that the workspace-tier record survived, and that `kb search` reaches all of them.

Until this lands, a cross-machine merge is still possible but not self-sufficient: it must be followed by `kb ingest` over every `decisions/` directory, and the operator has to know that without being told by the tool. The pending merge between this machine and wren.local is the immediate case. Two threads are left open deliberately — the schema-coverage guard, which would have turned this silent loss into an error message and wants its own record, and `sources` in `rebuildFTSIfNeeded`, which is noted here only so the next reader knows it was seen and left rather than missed.
