**Context.** W4 adds `kb record list|show|set-status|supersede` and W5 adds `new` and `fmt`, which between them make `kb` the first thing that *writes* a record file — ingest is forbidden from doing so. Four questions the plan leaves open surfaced across the two phases, and one defect surfaced from a design conversation rather than from code. The plan addresses records by bare id throughout (`record show 0160`, `supersede 0149 0148`), but an id alone is not an identity: two projects may each have a DR-0001, and the workspace tier has its own numbering besides. W4's text also says `set-status` should leave "every other line untouched", which presumes a surgical line edit and quietly creates a second writer with different rules from `RenderRecordFile`. The plan calls for `supersede` to write both sides "atomically" without saying what that means across two files and a database. And separately, while discussing whether to create `~/Laboratory/agents/decisions/` — a second workspace tier — DR-0006's note that `workspace:` does not say *which* workspace turned out to understate the problem: it is not only references that are ambiguous, but the records themselves. Ingesting two workspaces' tiers into one database was demonstrated to overwrite the first with the second, reported as a routine `1 updated`, with no warning and no way to notice.

**Decision.** A bare id is resolved across every tier, and where more than one record matches, the candidates are named and `--project P` or `--workspace` is required; picking the first match is never correct. `set-status` and `supersede` parse and re-render through `RenderRecordFile` rather than editing a line in place — one writer, one rule — and where the file was not already canonical they say so instead of normalising it silently. `supersede` validates both records and both files first, writes them in order, and restores the originals from memory if any later step fails, so the two sides and the relation row cannot drift apart. An incoming record whose `(project, scope, record_id)` is already taken but whose `uuid` differs is refused, counted as a failure, reported, and the run continues: a run should survive a collision, but data must not be destroyed by one. `record fmt` is file-only and never writes to the database, mirroring the rule that ingest never writes to a file; `record new` always writes `status: proposed` and requires `--trigger`.

**Rationale.** The re-render decision is the one that departs from the plan's literal text, and it turns out to satisfy the intent anyway: because 192 of the 198 records were already canonical, a whole supersession changes exactly the `status` and `superseded_by` lines and nothing else — verified by diff, not asserted. The alternative would have bought line-level fidelity at the cost of a second writer that `record`, `fmt` and eventually `index` would each have had to keep in step with the renderer, which is precisely the drift DR-0005 avoided by making the struct the specification. The collision guard keys on `uuid` rather than on a workspace registry because `uuid` is already a record's stable identity across machines, so the check needs no new state, generalises past the workspace case, and stays silent where it cannot conclude — when either uuid is empty, a changed `path` only warns, since a slug is cosmetic and may be regenerated at any time.

**Rejected alternatives.** Defaulting an ambiguous id to the only project that has one, or to the first match — convenient, and it makes `supersede` capable of silently rewriting the wrong repository's record. A surgical `status:` line edit, per the plan's wording — see above. True transactional atomicity across two files and a database, via a journal or a temporary directory — real atomicity is not available across a filesystem and SQLite without far more machinery than this earns, and validate-then-write-then-restore covers every failure mode that has a plausible cause here. Making the workspace tier's identity complete *now*, by carrying the workspace's own name — this is the right answer and it is deliberately deferred: it removes the NULL `project_id`, which would retire DR-0004's `IFNULL` index and change how every workspace record is stored, so it is its own effort rather than a rider on this one. Refusing the whole run on a collision — the run should survive; the record must.

**Consequences.** `go build`/`go vet`/`gofmt`/`go test` clean; 285 tests, none skipped. The guard was verified not to false-positive by ingesting and re-ingesting all five live corpora at 0 failed, and verified to fire by the two-workspace case it exists for, where the first record now survives intact. `kb record fmt` was run against `~/WorkLab/CMTools/decisions/` for real: 6 changed, 7 already canonical, and the diff is exactly the block-sequence-to-inline-list change DR-0005 predicted, with bodies untouched. `DECISION_RECORD_FORMAT.md`'s example was corrected to quote `uuid` and `origin_host`; its field table still says nothing about quoting those two, which is a smaller inconsistency left standing. Normalising CMTools made `TestParseRecordFile_RoundTripsEveryLiveRecord` fail, which is the test working in both directions — it asserted those six *would* diverge. Its exception set is now empty and the assertion is stronger: every one of the 201 live records round-trips byte-identically, with no exceptions at all. The companion test that checked normalisation touched only `decisions[]` became vacuous once nothing diverged and was replaced by a fixture-based equivalent in `cmd/kb`. This record is the first written by `kb record new` rather than by hand, which is what W7 asks for.
