**Context.** `TODO.md` recorded a concrete case: the `dev-process` project's description in `~/WorkLab/agents/knowledge.db` named `DESIGN_DECIDE_PLAN.md`, a file renamed to `DESIGN_REVIEW_PLAN_IMPLEMENT.md` the same day. A description is grounding context — it is what `kb project show` prints and what `kb search` returns as a snippet — so the stale filename kept being handed to sessions as current, and the only way to correct it was SQL against the database, which is the thing the CLI exists to avoid. `SetProjectStatus` was the only in-place mutation on a `projects` row, and it touches `status` alone. The request asked whether this was one verb or a general "correct a row you already wrote" pass, and asked that the write reconcile across machines under `kb merge`. Reviewing the code answered the first question and reframed the second: two of the request's three premises were wrong, in opposite directions.

**Decision.** `kb project set-description NAME DESCRIPTION` replaces a project's description, refreshes its `kb_fts` row, and touches `updated_at`. Trailing words join with a space, as `project add` already joins them; a bare `NAME` is a usage error and an explicit empty string clears the description, so a clear is always deliberate. `AddConceptWithIdentifier`'s `ON CONFLICT` clause now guards `description` the way it already guarded `identifier_type` and `identifier_value`: an empty one preserves what is stored. Observation bodies stay immutable. `MergeKnowledgeBases` and `ImportJSONL` are untouched, and `kb-project(1)` carries a CAVEATS section saying so in as many words.

**Concepts did not have the gap — they had the opposite bug.** The request listed `kb concept` among the add-only verbs. It was not: `AddConceptWithIdentifier` already carried `ON CONFLICT(name) DO UPDATE SET description = excluded.description`, unconditionally, while the two identifier columns on the next two lines were both guarded with `CASE WHEN excluded.x = '' THEN concepts.x ELSE excluded.x END`. So `kb concept add wal-mode` — with no description, which is a legitimate way to check for or re-assert a concept — silently wiped whatever description that concept had, in the row and in the FTS index both. `kb concept add` was already the "have `add` upsert" design the request rejected as too easy to trigger by accident, shipped and unguarded, and the accident it enables is data loss rather than a merely confusing write. The failing test came first and reproduced it exactly. The asymmetry looks like an oversight rather than a decision: whoever wrote the identifier guard had the argument in hand and did not extend it one line up.

**"Touch the merge columns" is a policy inversion, not a column touch.** The request's closing ask — that a description edited on two machines "reconciles under `kb merge` rather than silently picking one" — describes a change to conflict resolution, and the current resolution is not a coin flip. `MergeKnowledgeBases` is `INSERT OR IGNORE` set-union deduped by `uuid` and by the pre-existing `name` UNIQUE constraint, and it inserts `a` before `b` for every table, so **A wins deterministically** and `updated_at` is never read. `importProject` is explicitly the same policy, and DR-0003 argues for it: an existing local row wins as-is, uuid and description untouched. Beyond the policy, the columns are not there to touch — only `projects` has `updated_at` at all; `concepts` and `observations` have no such column, and the JSONL export selects `created_at` without it on both tables. Delivering the ask therefore means adding a column to `concepts`, extending `parentCols` and the JSONL record structs, and reversing a documented decision in two places. That is a larger and more interesting change than a setter, and it is not one a setter should carry in quietly, so this phase records `updated_at` faithfully and stops there. Nothing reads it across machines yet; recording it now is what makes the later pass possible.

**Rationale.** `set-description` over an upserting `add` is the request's own argument and it survives scrutiny: `add` returning the existing id is how a caller asserts a project exists without caring whether it did, and giving that path a write makes every such assertion a potential overwrite. `set-status` already established the shape, so the new verb costs a reader nothing. Observations are excluded on stronger grounds than symmetry would suggest: an observation is a *timestamped* note, append-only by construction, and "correct an observation" is the amend-versus-supersede question the `records` table answers with an explicit `supersedes` edge. Answering it by mutating `body` in place would decide it by accident. The FTS refresh is factored into `refreshProjectFTS` and does delete-then-insert rather than update, because `kb_fts` is a contentless FTS5 table with no unique key to upsert against — skipping the delete leaves a second row behind and lets `bm25` count the same project twice, which is why that is now pinned by its own test. The helper stays silent on failure, matching what `addProject` already did: search is an index over the real tables, so a failed reindex must not fail a write that has already committed. On the concept path, `RETURNING id, description` replaces the `LastInsertId`-then-fallback-`SELECT` dance and does necessary work besides — with the guard in place the argument passed in is no longer the description that landed, and `kb_fts` has to be indexed on the one that did.

**Rejected alternatives.** Making `add` upsert instead of adding a verb — terser, and the concept bug is what it looks like in production. Rejecting an empty `DESCRIPTION` on `set-description` for consistency with the concept guard — the two cases differ in exactly the way that matters: on a verb named `set-description` an empty argument is an instruction, on `add` it is an omission. A general `kb <verb> set-description` across all three entities in one pass — it would have required deciding observation mutation semantics first, which is a different decision with a different rationale. Adding `updated_at` to `concepts` now, in anticipation — a column no code reads is not groundwork, it is a migration to explain later. Fixing the concept clobber by making `AddConcept` refuse an existing name — it would break `kb concept add`'s documented idempotence, which `link` and `ingest` both lean on.

**Consequences.** `go test ./...` clean, `gofmt` clean apart from `version.go`, which `cmt` generates and which was already deviating. Twelve new tests: seven on `SetProjectDescription` covering status preservation, FTS refresh, the single-row invariant, the `updated_at` touch against a back-dated row, the explicit clear, and not-found; three on the concept guard including the FTS side; and on the CLI side the happy path, JSON shape, explicit clear, missing-argument, not-found, plus two guards that the subcommand appears in the verb's usage line and in `ProjectHelpText`. Verified end to end against a scratch database: the stale term stops matching `kb search` after the correction and the new one starts, and `kb concept add` twice no longer loses the description. `kb-project.1.md` and `kb-concept.1.md` regenerated; `KB_TOPICS` needed no change, since both verbs were already listed. Noted and not acted on: `kb search` exits 0 when it finds nothing, where the workspace convention for search-style tools is 1 — unrelated to this change and possibly deliberate here. Phase 2, if taken, is last-writer-wins across `merge` and `import`, and it needs its own record because it reverses DR-0003.
