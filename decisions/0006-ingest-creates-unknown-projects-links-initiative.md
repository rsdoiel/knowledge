**Context.** W3 implements `kb ingest PATH [--dry-run] [--root DIR]`, whose two passes exist so that a record may cite one the walk has not reached yet. The plan specifies the walk, the checksum skip, the `[<scope>:]<id>` reference grammar from design decision 6, additive-only deletion semantics, and the rule that ingest never writes to a record file. Four questions it does not answer surfaced while implementing, each of which the plan's own acceptance criteria turn out to depend on. The plan requires that "ingesting `~/WorkLab/clasm/decisions/` yields 169 records", which is unsatisfiable if a frontmatter `project:` naming a project the database has never seen causes those records to be skipped. It requires that ingesting the workspace tier before `clasm` leaves the cross-tier reference unwritten, exits 0, and "resolves it on a later run once `clasm` has been ingested" — but on that later run every workspace file is unchanged and therefore checksum-skipped, so if a skip also skipped resolution the documented remedy could never work. Design decision 3 settles that `initiative` is materialised as a concept link at ingest, and the W3 work items omit it entirely, so it would have been parsed and silently dropped. And the plan says ingest upserts into `records` *and* `kb_fts`, without saying which layer owns that.

**Decision.** A project named in frontmatter but absent is created, with `ProjectByName`'s "not found" reported as `(nil, nil)` rather than an error — a distinction that caused a nil dereference before it was noticed. `initiative` is materialised during pass one via `AddConcept` (upsert-by-name) plus `LinkProjectConcept` (`INSERT OR IGNORE`), both already idempotent. Pass two iterates every parsed record including the checksum-skipped ones, whose database ids come from the identity lookup pass one already performs. FTS indexing lives in `AddRecord`, delete-then-insert because FTS5 has no upsert, matching how projects and concepts are reindexed; records are indexed with `source_type = 'record'`, `label = DR-NNNN`, and the title prepended to the body so titles are searchable. Nothing about a reference is fatal: an unresolvable target, a qualified `supersedes` or `superseded_by` entry, and an unparsable file are each counted and reported in the run summary while the rest of the run proceeds.

**Rejected.** Reporting and skipping a record whose project is unknown — safer in isolation, but it makes a first ingest against a fresh database produce nothing, and the failure mode is silent under-population rather than a visible error. Resolving relations only for added and updated records — cheaper, and wrong for the reason above; the cost of re-resolving a skipped record is one indexed lookup per reference, against a corpus where 42 relations exist across 198 records. Putting FTS maintenance in `ingest` — it would work today because ingest is the only writer, but `kb record new`, `set-status` and `supersede` all land in W4 and W5 and would each have had to remember to do it. Deferring `initiative` because no live record populates it (0 of 198) — the field parses, the design settles its handling, and dropping it silently is worse than covering it with a fixture test.

**Consequences.** `go build`/`go vet`/`gofmt`/`go test` clean; 24 tests in `cmd/kb/ingest_test.go`, 247 across the module, none skipped. Verified end to end with the built binary against all five live corpora into a scratch database: 198 records (192 project-tier, 6 workspace), 42 relations, 198 FTS rows, zero failures. `clasm` reports "169 added, 2 supersedes, 3 relates_to" and a second run "169 skipped, 0 updated", both exactly as the plan specifies. Order independence was confirmed the hard way rather than asserted: ingesting `agents/decisions` *before* `clasm` exits 0 with the `clasm:0160` reference reported as unresolved, and a re-run after `clasm` lands takes `relates_to` from 7 to 8 and resolves it — the first cross-tier reference in existence, now stored. `clasm` DR-0160 remains `accepted` while carrying its supersession, confirming on real data that `superseded_by` does not imply `status: superseded`. One gap this leaves for W6: `Search` still reports a record's own `kind` rather than `record` as the result type, because the FTS row stores `kind` in that column; the `label` is already `DR-NNNN`, so W6's criterion needs only a change to `Search`'s projection. A second, smaller finding worth recording: the `workspace:` reference qualifier names "the workspace tier" without saying *which* workspace, which is unambiguous today only because `~/WorkLab` is the sole workspace with a populated `agents/decisions/`. A record in `~/Laboratory/knowledge` citing `workspace:0002` would resolve against `~/Laboratory`'s workspace tier, not WorkLab's. No such reference has been written, and none should be until the grammar says which workspace it means.
